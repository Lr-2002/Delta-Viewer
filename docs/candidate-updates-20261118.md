# 软件内公开候选更新（1.11.6 开发候选）

> 2026-11-18 最新澄清：用户要求的是“必要验证及本人确认后尽快提前更新”，不是在正式发布前再复制完整 GitHub 候选发布流程。后续目标顺序为必要测试和可分发安装包预览 → 用户验收 → 复用同一包直接投放软件内更新／内网 → 完整 GitHub CI 及三平台正式 Release。复用已有检查，客户端既有自动验签由构建处理，不新增人工往返。下述依赖 GitHub 候选构建的机制属于当前实现，尚未完成快速路径简化，不能把规划当作已经实现。当前 1.11.6 CI 已成功，内网已提供手动安装供验收，全员软件内更新仍待用户明确确认。

用户要求先在软件内提供候选更新，验收合格后再构建三平台正式安装包和发布 GitHub，并选择所有用户接收候选。安装始终由用户主动确认；后台检查不自动下载、退出、重启或替用户保存审核结论。旧窗口、登录、草稿、生产数据和设备工作树保持。

旧客户端将官方已发布 Release 作为更新身份，无法在不改客户端的情况下接受尚未发布的候选。首次需要安装一次支持此通道的新版本；不能宣称已向仍运行 1.11.4 的所有用户投送。支持后的客户端在启动与既有半小时检查时同时读取候选和正式版本，选择较新版本，同号优先正式身份。任一路失败可以沿用另一路；失败不影响现有工作。候选清单没有当前平台时该平台沿用正式更新。候选提示明确尚未正式发布，更新按钮沿用保存、忙碌、下载验证与用户确认。

固定候选来源为 `https://114.111.19.219/api/manager-updates/candidate`，与业务账号凭据无关。只接受有效 TLS，不允许重定向、任意来源或前端自定义地址。`latest.json` 是包裹 JSON：payload 为 Base64 编码的原始清单字节，signature 使用既有应用内嵌更新公钥核验该原文。校验签名后再解释 schemaVersion、candidate 通道、标准递增版本、完整源码 commit、日期、中文摘要与所含的平台清单。元数据最多 1 MiB；每个更新包仍 1–64 MiB，检查固定 URL、实际大小、SHA-256 及独立 Minisign 签名。Windows 仍明确 UNSIGNED，更新签名不提供可信发布者身份。

候选与正式源互相独立，不将候选伪造成官方 Release、写入正式镜像最新指针或创建公开 tag。公开候选版本不可覆盖或扩展平台集合；有新内容或需要补平台时分配新版本。完整正式流程仍要求用户验收、main CI、自动 tag、三平台原生门禁与签名集合，不允许候选通过替代正式门禁。

`.github/workflows/candidate.yml` 先运行与 CI 一致的完整检查，再绑定 exact commit，默认只构建 Windows。手动触发可选 macOS、Ubuntu 或 all；各平台复用既有资源、原生构建、安装／启动／卸载和 unsigned 校验。工作流只上传签名候选 artifact，不发布 GitHub Release。`scripts/candidate-updates.mjs` 准备、核验清单与包，签名仅在 GitHub Secret 对应步骤可见，再生成外层清单。发布者从成功 workflow 下载该 artifact，先 verify，再 publish 至专属只读 HTTPS 目录；发布不依赖或修改用户中心、审核或设备服务。原子更新最新指针，拒绝旧构建降版本，同版本仅允许完全相同字节的重试。实际公网启用及当前候选身份另按部署回执核实。

后续每轮顺序：更新版本和中文摘要 → 完整检查 → 所需平台候选构建和签名 → 验证 artifact 并投放软件内候选 → Windows／用户验证 → 确认验收源码 → 三平台正式 GitHub Release。首次引导安装另向用户明确说明；不能为了测试安装而关闭其保留的旧窗口。

## 内网首次安装入口

内网旧服务只同步 GitHub 正式 Release，因此新候选没有自动出现在内网页面。分发维护补充独立候选安装入口：发布者先核对成功候选工作流、源码 commit、包的大小／哈希／签名及 Windows 安装／启动／卸载报告，再原子放入内网版本目录，最后写 `candidate-downloads.json`。页面将候选版本、尚未正式发布、Windows 下载与 SHA-256 单独列出；旧正式下载及 `/client/latest.json` 身份不变，不伪造旧版能够自动接收候选。

此修改仅用于内网更新服务，不改 Manager 编译产物。可在独立分发分支维护，候选二进制仍绑定其原始构建 commit。无候选文件、元数据异常或包大小不符时，页面继续提供已验证正式版本。当前已备妥源码和回归，是否实际上架以安装包发布及 HTTP 下载验证回执为准。

2026-11-18 构建维护：Windows Git 的自动 CRLF 转换会让旧版源码身份脚本误报 Cargo.lock 版本不匹配，构建现在在 checkout 前关闭自动换行转换，仍核对 exact commit 和 clean source。Linux 包下载使用固定 HTTPS Ubuntu 镜像并设置重试、读取与步骤截止时间。原生构建与完整检查可并行，只有全部所选平台及 gate 均成功后才组装签名候选。一次性恢复工作流固定软件源码为已打开 Windows 预览的 1f7cf707efcae53b724944528d2a0588ea538658；工作流维护提交与软件源码提交分别记录，不把它们混为同一 SHA。
