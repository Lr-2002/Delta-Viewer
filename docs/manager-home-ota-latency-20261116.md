# 首页入口与版本检查等待核对（1.10.4）

日期：2026-11-16。基线：正式 1.10.3，commit `43cb420abc54fe04d0ba534afe5f8afb78b76b5a`。

## 用户可见变化

首页连接控件、黄色操作提醒和功能入口组成统一面板。设备管理、设备信息、检测排障为三个等宽入口，图标、标题、用途与箭头对齐；连接结果和实际地址位于工作区标题行，设备版本与健康摘要收在底部。桌面横排、窄窗口纵排，保持键盘焦点和禁用状态。连接成功仍停留首页，点击入口才进入页面；AP 仅配置时不开放信息／检测，原黄色提醒位置保持。

检查版本不提前下载制品。设备版本与源站目标不同时，本次 SSH 状态读取已核对实际版本、身份和主机指纹，不再额外执行只会再次读取版本的 check。二者一致时仍由设备端再次确认 VERSION 和 RELEASE，记录准确的 UP_TO_DATE；仅语音改为独立固定任务，不改变版本判断。

## 响应慢的证据与适用范围

现场 Windows 正式 1.10.3 的只读原生 IPC 分段测得：

| 环节 | 实际结果 |
| --- | --- |
| `d1_ota_preview`，读取当前 Factory 元数据 | 18ms，版本 1.3.1，五文件描述符 |
| `d1_ota_status`，Type-C SSH 状态，连续三次 | 420ms／300ms／293ms，实际版本 1.3.1 |
| Windows 直接 HTTP 探测 | 域名请求约 62ms；固定 IP 请求约 16ms |
| Linux 首次域名请求 | 4,154ms；随后固定 IP 请求约 16ms |
| Linux 三轮四个元数据资源 | 每轮合计约 54–69ms |

当时固定源站为 `http://deltadevice.cn:4174`，解析至 `10.1.40.10`。以上只证明这些请求当时的耗时；首次请求曾慢约四秒，源站或链路波动可能增加等待，不能据一次快速请求排除上游问题。

代码确认原检查顺序为源站预览 → SSH status → SSH check。相同版本时 check 同步调用设备音频播放器，等待共享音频锁和播放结束，子进程最多等待 20 秒。因此，源站已经返回也可能继续显示检查中。此次没有对实体调用 check，以免触发语音和设备日志写入；不把代码时限当成已实测的完整用户等待，也不声称已量出全部时间分布。

## 语音独立执行与一致性

设备端先持久保存本操作的请求、版本结果和最新操作指针，再以固定脚本和固定参数启动 systemd 语音任务。启动命令最多等待三秒，独立任务最多运行三十秒；仍调用设备已有音频模块与共享音频锁，尊重设备语音配置。

语音任务按操作目录加锁，播放前持久标记 playing。重复请求、重复任务和并发执行不再重播；语音启动回执超时可能发生在任务已启动之后，失败处理也必须取得同一锁并重读 queued 状态，不能覆盖正在播放或已经完成的记录。语音完成只更新自己的操作日志，不修改最新操作指针。语音失败只给出提醒，UP_TO_DATE 保持有效；播放中崩溃不会自动重播。

保留相同版本号但不同发布批次的区别、账号隔离、真实 CID／UUID、主机指纹、预览归属和时效、大小／SHA-256、源站具体错误、活动任务与 UNKNOWN 阻断，以及后续安装的供电、温度、包架构和健康门禁。既有三种连接方式均走固定 SSH 执行器。
