# 用户中心响应、统一写回与版本状态诊断（1.6.0）

2026-11-04。本次处理共用服务和客户端协议，不以截图所在电脑作为修复范围。

## 原因与现场证据

用户中心 `/api/v1/admin/reviews` 原先在 HTTPS 主线程同步聚合 SQLite。监管页面每三秒刷新，原始库已有约 904 万条操作事件、约 4.1 GB。只读测量中，操作、在线与会话聚合分别超过 12 秒仍未完成；监听队列曾有 228 个等待连接。服务进程未退出，空闲时 health 约 3 ms。因此统计请求会间歇性堵塞登录、版本上报、审核事件接收和写回回执，不能将连接超时直接解释为 NAS 满盘或某台电脑故障。

统一写回还有两个独立显示问题：客户端曾将“轮询没有新指令”当成回执已确认，且已经确认完成后发生普通轮询失败，也会重新显示写回未确认。管理端则把离线设备的旧待写数量一起累加，版本新鲜度受客户端系统时钟偏差影响。

内网安装包服务 `17879/latest.json` 当时约 2 ms 返回 1.5.9，与用户中心 `17880` 独立。账号版本与推送状态受用户中心影响，不等于安装包服务器故障。

## 修复与行为

- 统计移到只读 worker；普通总览和筛选分别排队，同请求合并，每个通道最多八项。八秒未算完返回明确的计算中提示，后台继续，控制请求保持可响应。
- 普通全历史统计使用独立、可重建的 SQLite 增量摘要。保留原事件去重、会话最后结论和本机已提交结论计数规则，不更改原事件或 NAS 结果。源库身份或游标不符时拒绝使用旧摘要。
- 真实规模首次整理 9,039,992 条事件耗时 33.89 秒，下一次增量与摘要查询约 11.76 ms。此为该次现场测量，不代表所有筛选都在该时间内完成。带筛选的历史查询仍可能较慢，但不占 HTTPS 主线程。
- 写回确认必须匹配服务端持久保存的 requestId 和序号；普通成功不能替代对应回执或掩盖部分失败。已确认写回与后续连接异常分别说明。
- 待写数量只汇总最近 90 秒内有效在线设备；离线、异常和历史回执分开显示。版本与待写新鲜度使用服务器时间和本机单调经过时间，避免系统时钟偏差。没有数据时显示未知及原因，不虚构零值。
- 真实在线上报可证明应用在线，但不构造审核操作，不增加有效耗时；通过与不通过均计入已提交结果，120 秒无操作扣除规则保持。

## 验证

`pnpm check:full` 通过，包括前端构建、Rust 检查和原生 debug 构建；Rust 常规测试 282 项通过、17 项按环境要求忽略，另有三个 CLI 测试通过。用户中心、版本管理、审核同步和统一写回浏览器回归通过。

隔离测试覆盖跨 20,000 条增量边界与原聚合等价、迟到事件、重复事件、撤回、NAS 确认、重启、独立账号；CPU 忙统计期间 health、在线上报、版本和写回轮询继续响应。另验回执不匹配不能确认、无关成功不能清失败、断线恢复、服务器与本机相差一小时时仍准确显示版本。部署版本保留主机 output_provenance 扩展，并用隔离 HTTPS 验证其可写可读及重启续接。

三平台正式安装包由既有 CI/CD 构建和验收；本机 Linux debug 构建不能替代 Windows/macOS 安装验证。

## 仍需区分的状态

现场两个账号的现有写回回执确有 `storage_unavailable` 和 `conflict`，分别有 100、924 条仍在本机。服务恢复不会自动证明这些已成功写回；软件保留结果及冲突保护，需在原客户端检查具体待写项，不能覆盖他人更新。此次未向真实审核员下发测试写回或更新提醒，未代审真实数据。

用户中心确认接收、NAS 持久写入、工作台完成统计是三个不同状态。不得宣称历史十条缺失事件已恢复，亦不因普通请求成功清除真实异常。本次只部署用户中心独立目录，保留证书、账号、领取与所有审核队列，不修改受校验的原流水线发布目录，不重启工作台或上传服务，不调整 NAS/RAID。
