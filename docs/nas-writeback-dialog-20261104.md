# 统一写回自动提醒协调（1.6.2）

## 实机发现

1.6.1正式安装到Windows目标机10.1.41.119后，使用独立账号、WebView缓存和三个隔离SMB目录验证：第一轮已检查3条、写入1条、失败2条（目录无法访问、已知QC冲突），与实际文件一致。恢复夹具后再次下发，设备持续busy而不处理。

截图与DOM证明：SourceReviewNotice定时检查存储恢复后自动弹出“本机审核结果待写回”；SourceWritebackClient检测到任意打开的dialog便等待。这两个正确的单独功能组合后，自动提示变成统一写回的额外人工前置步骤。手动点“稍后”后，原已下发指令随后写入剩余2条；直接读取三个description.json/session.json，均为原审核人、原日期和通过结论，人工审核信息仍只含3字段。未改真实审核结果。

## 修复

管理员指令被成功鉴权接收后，客户端发出仅本机有效的账号/service协调通知；同账号且没有人工介入的自动恢复弹窗收起，存储轮询不再重新弹窗阻塞指令。通知本身不执行人工发布、不生成审核操作，也不替代原生owner校验、共享文件保护或TaskControl。

手动打开、通过指针/键盘/滚轮介入的核对窗口和手工写回保持；其他对话框、播放和未存改动仍须结束后执行。不同账号或service不能关闭此窗口；退出/切换账号解除旧协调。部分失败仍保留本机和持续提示，不将普通网络成功当补写成功。

## 验证与交付

组合浏览器回归覆盖先自动弹窗再收管理员指令、不人工关窗即可执行、后续刷新不重开阻塞、其他账号通知忽略、人工接管自动窗、手动打开窗口及切换账号。原恢复提醒的显式确认、失败保留及窄屏按钮回归保持。

本提交正式版本1.6.2，包含1.6.1全部队列/兼容/真实数量修复。三平台Release和目标机新一轮无需手动关闭弹窗的补写，以对应流水线及diagnostics/delivery-1.6.2现场记录为准。用户中心沿用已部署且兼容的1.6.1服务端，无新后端修改或重启。不重启工作台/上传，不动NAS/RAID，不向真实审核员发送测试写回或更新弹窗。

旧版升级后，对已终止的旧指令重新点“写回”。真正的共享冲突或不存在目录仍需核对，不能声称所有真实历史积压或缺失记录已恢复。
