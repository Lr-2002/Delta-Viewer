# 目录编号变化后的机标加载（1.1.2）

## 现象与调查结论

`MACHINE_ANNOTATION_INVALID: 机标 episode_id 与当前数据目录不匹配` 表示机标内部记录编号与当前采集目录名不一致。JSON 存在、格式合法、帧数相同，都不能独立证明属于当前视频。旧解析器只接受目录名完全相等，所以随目录移动但仍保留旧编号的机标会被拒绝，动作片段显示为零；视频本身仍可回放。

本次对用户指定 NAS 记录只读核对：目录名与机标 `asset_id`/主结果 `episode_id` 不同；主相机帧数一致，按生产端实际算法复算的 `quality.source_fingerprint` 也完全一致。相邻样例出现相同方向的编号偏移，支持目录重新编号而机标内容保留旧编号的解释；没有改名操作历史，不能确定由哪个程序或人员在何时改名。私有路径、机标及精确取证明细只留本机报告。

该指纹是**文件元数据指纹**，由文件相对名、大小、修改时间组合计算 SHA-256，不是整个视频内容的 SHA-256。它沿用百炼生产端 `auto_item_fingerprint` v3 协议；不能据此承诺识别内容被修改但大小、时间被刻意保留的情况。审核员仍需回放核对动作。

## 新版选择逻辑

1. 优先保留目录名与 `episode_id` 的精确匹配；精确结果重复仍报歧义。
2. 无精确结果时，要求顶层 `asset_id` 唯一指定一个主结果。多 episode 可能共用同一来源指纹，不能随意选择第一个，也不合并不同动作周期。
3. 仅对当前目录平铺的 `cam0/cam0-00000.mp4` 等五位编号分段核验生产端文件元数据指纹，并核对当前主相机帧数。所有条件同时成立才兼容加载。只枚举当前 cam0，最多 4096 个条目，不读视频字节、不扫描整个批次。
4. 动作片段区持续显示目录编号、原机标编号及核验依据。机标源字节、哈希、原编号和未改字段保持原样；正常人工保存沿用原身份写入 `description.json`，支持本机与新主机重开。
5. 指纹缺失或不符、帧数不符、主结果不唯一、链接、未知命名、JPEG/BIN/嵌套视频等未支持协议仍拒绝猜测。提示两侧编号，并指引选择其他来源，或切换“人工标注”后点击＋重新标注。

源数据被复制或重新写入导致修改时间变化时，指纹可能无法复核；不会自动忽略时间差，也不会尝试数字偏移。NAS 共享应保持原修改时间。未经人工确认不会修改源机标、批量重编号或更改历史 QC。

## 回归与现场核验

隔离测试覆盖正确/错误指纹、相同帧数但错误来源、帧数不符、缺失 asset_id、重复主结果、主结果不是数组首项、精确匹配优先、源文件改变、原机标不变，以及人工保存并在新主机数据目录重新读取。固定生产端指纹向量跨平台验证纳秒时间编码。

浏览器检查 1440、960、390 像素宽度下编号差异提示可见、可编辑且不横向溢出；Windows 发布门禁额外运行原生机标回归。真实 NAS JSON 与文件元数据在本机隔离还原（MP4 为稀疏占位，不用来宣称视频解码通过）验证解析；Windows 交互会话只读核对共享盘原始修改时间。发布后的 Windows 原生程序还需对真实只读共享目录运行显式样例测试；结果记录在交付报告，不用模拟数据冒充现场验收。
