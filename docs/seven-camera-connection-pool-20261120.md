# 七路视频连接竞争调查与候选修正

日期：2026-11-20；开发候选：1.12.8。

用户确认卡顿截图来自1.12.7预览，本地任务与外发审核均出现。截图中主路为4K、七路共同等待，但未带请求时序与解码数据，不能单凭截图判定磁盘、网络或GPU，也不能把连接池问题说成全部卡顿的唯一根因。

## 可复现的读取阻塞

两个原生媒体服务均向浏览器提供单一本机HTTP/1.1地址。本地普通范围最长32MiB，外发16MiB；浏览器因缓冲额度或暂停对正文施加背压时，连接可以保持占用。Chromium对同一地址最多并行六个HTTP/1.1连接，七相机的后续读取可能排在仍未完成的健康镜头后面。短文件很快结束时不明显；长响应、拖动重读或多路缓冲竞争时容易放大。

独立七video夹具用内存响应保持正文打开：前六路在约193–204ms到达，第七路在释放一路后约1521ms才到达。改为独立回环地址后，其他响应保持打开时七路全部开始请求。此对照确认浏览器连接排队机制，不是Manager真实产物的七路流畅验收；原始证据仅保存在本机diagnostics，不含源媒体或生产票据。

## 修正范围

- 七个相机分别使用随机IPv4回环端口。端口只监听127.0.0.1，不增加网络暴露，不改变视频内容、分辨率或帧时钟。
- 本地原片、显式本地缓存原片、已有自适应预览清单及其片段均按同一相机分配地址。未知相机保守使用主路地址；正常七路各自独立。
- 外发前端从实际相机槽位提供mediaLane=0–6。Rust在请求交付平台前移除此本机调度提示，严格校验范围；上游来源仍仅由已认证video-url响应确定。
- 七端口共用原有16活动连接额度，保持每请求最多四个1MiB上游分块、随机路由、账号复核、票据释放与断连取消。状态、逐帧元数据与释放仅接受本服务实际绑定的端口，仍拒绝其他本机服务地址。
- 修复暂停后跨高速浏览倍速阈值未立即发布新位置的问题。保留原回归54不应等于72的断言，只改生产代码的即时通知。

Rust原生回归覆盖七个不同地址的真实Range正文、源文件未变，以及外发七端口的访问、错误端口拒绝、统一释放失效。既有外发回放回归增加七相机调度接线断言。媒体测试单独初始化既定Rustls provider，避免孤立运行依赖其他测试先初始化。
